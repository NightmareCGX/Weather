## 19. 实现记录：已落地的部分与未落地的部分

§1–§18 是调查与决策。本节记录**实现过程中出现了什么**，尤其是那些调查阶段没有预见、只有真写代码才会暴露的问题，以及 D 类为什么至今没有接入服务路径。

### 19.1 两个在实现中才暴露的缺陷（都已修复）

**（1）逐成员聚合：把"一个成员的统计量"当成了统计量。** 最初的接线在**每个成员的 COMPLETE marker 之后**就调用一次聚合趟。因为聚合是整套成员的函数，这既写出了 `MEAN = 281.0`（只含成员 1）、随后 `282.0`、`283.0` 这种**看起来像统计量、实际不是**的值，又因为该趟会删除它消费掉的 staging，把后续成员需要的 staging 一并销毁。成员不会重新 staging，因此这种损坏**不可恢复**（只能重跑整个周期）。修复：聚合只属于"结算"（85% 覆盖 + 静默期）这一独立趟。

**（2）patch 删掉了下一次 patch 需要的 staging。** 静默期发布先把当时已提交的成员聚合，然后**按"最终版"的语义删除了 staging**。于是下一次 patch 只能聚合"自上次以来新到的成员"：27 个成员的第一次发布之后再来 3 个，第二次聚合出来的是这 3 个的统计量，而不是 30 个的。容器本身完全合法、描述符里的成员数也自洽，**下游无法察觉**。修复：只有"本时效不会再增长"的发布才释放 staging；`publish_settled_lead` 增加 `aggregate_is_final` 参数，由波次按"完成路径 / 判定为 complete-or-final"置位。

这两个缺陷的共同点值得记下来：**它们都产生结构合法、数值错误、且事后不可检出的产物**。所以两者都用"把修复回退掉则测试必须失败"的方式固定（回归测试绑定缺陷，而不是绑定代码）。

### 19.2 `member_count`：一个必须持久化的量

`EnsembleStatisticsData.member_count` 是必填字段，语义是"**该点上**有限成员数"。聚合把成员塌缩掉之后，容器里**没有**这个数；写入时是知道的，但既没持久化也不是逐点的。

解决方式：把计数写进 v2 容器的**描述符**（占用原 8 字节保留区中的 4 字节，描述符仍是 40 字节，布局未变）。读端在**同一次尾部 range-GET** 里就能拿到它，无需第二次读。逐点语义则由两种编码都具备的性质给出：**任一成员在某个格点非有限，该格点所有字段都非有限**（`compute_aggregate` 的显式语义），因此"该格点字段全有限"⇔"由整套成员算出"。于是逐点答案 = 观测到则返回容器里的计数，否则 0；容器没有计数则返回 `None` 让调用方走成员路径——**不编造**。

（旧版读端会因为保留区非零而**直接拒绝**新容器，这是安全的方向，所以格式版本字节不需要变。）

### 19.3 读端接入的能力边界（实现后确认）

`aggregate_can_answer` 把"能由聚合回答"收敛成三条可判定条件，其余一律走成员路径：

| 条件 | 原因 |
|---|---|
| `include_members=true` | 请求的是原始成员样本，聚合已把它塌缩掉 |
| 四个按成员语义定义的变量 | `wind_10m` 的 consensus/rose 是逐成员 `(u,v)` 的函数；`precipitation_amount_3h` 的 phase support 是逐成员 0/1 标志的函数；`cloud_ceiling`/`cloud_cover_3h` 在汇总前**逐成员**做了删失/区间裁剪 |
| `gte`/`lte`/`between` | 需要阈值处的原子质量；见 §14.10（50% 恰为 0 的场：成员路径 `P(x≥0)=1.0`，聚合连续插值给 0.50，两者都不是） |

**结算发布本身不需要新端点**（这是实现中的一个重要简化）：`stats` 与 `include_members=false` 的路径都能完整服务，而 `include_members=true` 只是**同一个信息集加上原始样本**。因此聚合档发布后，`include_members=true` 对已转换变量取成员分片、其余取聚合即可，前端不需要"两套数据源"的复杂适配。

### 19.4 D 类为什么仍未接入

D 类的批准表示是**每格点超越比例**。实现时确认了两件事：

1. **标志变量确实在真实管线里**（`parser.py` 映射 `crain`/`csnow`/`cfrzr`/`cicep`，`idx_parser.py` 也把它们列为可下载字段），所以"没有真实数据"不是理由。
2. 但**公开 API 不单独暴露标志值**：它们只作为 `ensemble_data.py` / `point_forecast.py` 的内部输入，用来构造 `precipitation_amount_3h` 的相位（`classify_precipitation_phase`），而那条路径本身因 §19.3 第 2 条必须读成员。前端 `Meteogram` 测试里的 `crain: 0.65` 是**相位概率**（`phase_support`），不是标志场。

结论：**D 类的分类决策已落地**（`domain.variable_class` 里四个标志是 `is_flag=True`、`spec=None`，并说明"比例而非 `AggregateSpec`"），但**比例场本身没有写**：`aggregate_writer` 能编码任意单字段容器，但没有哪条代码路径生产该字段。接入的收益是零——没有公开的按标志查询接口，而相位路径无法由聚合回答。因此 D 类**不接入服务路径**，并在 staging 处显式保留其成员（`aggregate_lead_all_variables` 遇到无 spec 的变量时记录 "staging is retained" 并跳过，而不是静默丢弃）。

**唯一会让它变成有收益的例外**：若将来把"某相位（如冻雨）的集合概率"做成**公开**接口，且其定义是纯计数（不掺入 `temperature_2m` 等逐成员判据），那么 D 类比例场恰好就是它。届时接入是增加一个查询分支，不是新增一种编码。

### 19.5 已批准但**尚未接入写入路径**的量化定标（M9 阶段实测发现）

§18.5 批准"分箱定标改 `int16 @0.001`"，`domain.aggregate` 里 `quantise_field` / `check_quantisation_range` / `encode_aggregate` / `decode_aggregate` 都已实现并测试。**但生产写入路径从未调用它们**：

* `aggregate_from_planes` 直接把 `compute_aggregate` 的 **float32** 场交给 `encode_aggregate_shard`；
* `AggregateShardLayout.to_descriptor()` 硬编码 `encoding_id=ENCODING_F32, scale=1.0`；
* 格式层只认识 `f32` 一种编码（`ENCODING_NAMES = {1: "f32"}`），并且 `parse_descriptor` **拒绝** scale≠1.0 的容器——这是刻意设计（防止声明了 scale 却存 floats 的容器被静默缩放），但它同时意味着**只加 `int16` 不换 `encoding_id` 会被读端拒绝**；
* 量化尺度是**逐字段**的：A 类的 MEAN/STD 是 `0.01`（314 K → 31400，int16 放得下），分箱是 `0.001`（比值 ∈ [0,1]）；C 类全部 `0.01`。若沿用单 scale 字段，MEAN 在 `0.001` 下是 314000，**溢出 int16**。

在真实 GEFS f006 上用**同一个写端**实测这项缺口的代价（把场先按 spec 逐字段量化再反量化，隔离"量化"本身）：

| 变量 / 时效 | 现状（float32 场） | 按批准设计量化后 | 收益 |
|---|---|---|---|
| `temperature_2m` f006 | 17.73 MB | **13.54 MB** | **1.31×**（−4.2 MB） |
| `precipitation_amount_3h` f006 | 18.13 MB | **13.66 MB** | **1.33×**（−4.5 MB） |
| `temperature_2m` f240 | 15.40 MB | **11.12 MB** | **1.39×**（−4.3 MB） |

即**每个 `(变量, 时效)` 约 4.2–4.5 MB 是可回收的**，而且这是**无损的**（量化误差 ≤ scale/2，即 0.0005 的概率单位 / 0.005 K）——不是 §15 里那种需要拍板的精度取舍。整周期量级取决于变量数与时效数，但按此单价（约 14 变量 × 81 时效 × 4.3 MB ≈ 4.9 GB/周期）**与 §17.2 "整周期省 12 GB"同量级**。

**尚未做的就是上一步**：给格式加一个量化编码 id（`i16` + 逐字段 scale 表）、让 `to_descriptor` 从 spec 取 scale、让读写端按编码 id 分派、并把编码后的**字节**（而非 float32 场）交给容器。这是一次**容器格式变更**，会让只认识 `f32` 的读端拒绝新容器（安全方向），因此需要与 M2 的版本策略一并设计。

> 这一条是"实现会暴露调查发现不了的东西"的第三个实例：调查阶段的"收益"是在**场**这一层算的，而写端当时还没写；等写端落地，才发现它拿的是未量化的场。
